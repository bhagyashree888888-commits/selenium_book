1. What is API testing and why is it important?
API testing is the process of verifying that Application Programming Interfaces work as intended.
It ensures not only that APIs return the correct data, but also that they meet functional, performance, and security requirements. 
Unlike UI testing, which focuses on the front-end, API testing validates the business logic layer, ensuring endpoints correctly process requests and return expected responses.
API testing is important because APIs are the backbone of modern applications, particularly microservices. 
Issues at the API level can affect multiple downstream systems, and API tests provide faster feedback since they execute more quickly than UI tests.
For example, in an e-commerce application, the Add to Cart API must correctly handle stock availability, pricing, and user authentication before the UI can display it.

2. What are the different types of APIs?

1. APIs by Architecture / Style
🔹 REST API (Representational State Transfer)
REST is the most commonly used API architecture today.
It uses standard HTTP methods such as GET, POST, PUT, and DELETE.
REST APIs typically exchange data in JSON format, but they can also support other formats like XML, HTML, plain text, CSV, and multipart form data through HTTP content negotiation using headers.
REST APIs are stateless and lightweight, which makes them scalable and easy to maintain.
//REST Does not have built-in standards for security or transactions.
Example: Web and mobile app backends
Uses: URL + query parameters / request body
Format: HTTP (JSON usually)
GET /users/1?fields=name,email

🔹 SOAP API (Simple Object Access Protocol)
SOAP is an older, strict standard for APIs that primarily uses XML.
It has built-in support for security and transactions, making it suitable for critical enterprise applications.
SOAP is generally heavier and more rigid than REST, but it is still widely used in enterprise and banking systems where reliability and strict standards are required.

[  SOAP does not natively support JSON, HTML, CSV, or plain text. ❌
You can technically wrap other formats inside XML, but that defeats the purpose of SOAP.
If you need multiple formats, REST or GraphQL is the modern choice.    ]

Uses: XML request body
Format: XML over HTTP
eg:<soap:Envelope>
  <soap:Body>
    <GetUser>
      <UserId>1</UserId>
      <Fields>
        <Field>name</Field>
        <Field>email</Field>
      </Fields>
    </GetUser>
  </soap:Body>
</soap:Envelope>

🔹 GraphQL API
GraphQL is a query language for APIs where the client can request only the required data, so it does not receive unnecessary information.
It uses a single endpoint for fetching and manipulating data, which helps reduce over-fetching and under-fetching.
GraphQL is widely used in modern frontend applications, for example at Facebook.
//Uses: Single endpoint + query body
Format: GraphQL query (JSON response)
{
  user(id: 1) {
    name
    email
  }
}

🔹 gRPC (Google Remote Procedure Call-oldname)
gRPC is a high-performance RPC framework that uses a binary protocol with Protocol Buffers (Protobuf) for serialization.
It is strongly typed and designed for efficient communication between microservices.
gRPC is commonly used for internal service-to-service communication in modern distributed systems.

//for understanding
1️⃣ RPC framework
RPC = Remote Procedure Call
A way for one service (or program) to call a function in another service, just like calling a local function.(core principle)
Think of it as: “Service A says to Service B, ‘Hey, do this task for me,’ and gets the result.”

2️⃣ Protobuf (Protocol Buffers)
A way to format data so it can travel fast and compact between services.
It’s like a shorthand language for sending data, much smaller and faster than JSON or XML.
Backend engineers define a schema to ensure both sides understand the data.

3️⃣ Serialization
Serialization is the process of converting an in-memory object (data structure) into a format that can be transmitted over a network or stored, so that it can later be reconstructed (deserialized) into the original object.
Think of it as packing data to send it somewhere and then unpacking it on the other side.
Example:
A JavaScript object → convert into bytes (binary) → send to another service → convert back into object
Protobuf handles this conversion automatically and efficiently.
//Uses: Protobuf messages
Format: Binary over HTTP/2
GetUserRequest {
  user_id: 1
  fields: ["name", "email"]
}

🔹 WebSocket API
A WebSocket API establishes a full-duplex (is a communication channel where data can flow simultaneously in both directions), 
persistent connection between a client (browser or app) and a server, enabling low-latency, bidirectional communication.
It is commonly used in real-time applications such as chat platforms, online multiplayer games, live notifications, and collaborative tools where instant updates are critical.
//Uses: Persistent connection
Format: Custom message (JSON/text)
{
  "action": "getUser",

  "fields": ["name", "email"]

2. APIs by Access Level
🔹 Public (Open) APIs
Public APIs, also called open APIs, are accessible to anyone and often require an API key for identification or access control.
They are commonly used in services like weather apps, mapping platforms, and other third-party integrations, allowing developers to build applications on top of existing services.

🔹 Partner APIs
Partner APIs are shared only with specific business partners and are not publicly accessible.
They are more secure than public APIs and are commonly used in integrations such as payment gateways, logistics services, or B2B platforms.
[Logistics services = planning, implementing, and controlling the flow of goods, services, and information from the point of origin to the point of consumption.]
Backend integration base url: https://api.razorpay.com/v1/

🔹 Private (Internal) APIs
Private, or internal, APIs are used only within an organization and are not exposed to external users.
They are commonly employed to enable communication between internal systems or microservices, ensuring security and controlled access.

1️⃣ Internal Microservices
An e-commerce platform:
InventoryService API provides stock data to OrderService
Only accessible within the backend system

2️⃣ Internal Dashboards
HR or Finance dashboards call internal APIs to fetch employee or payroll data
Example: GET /employees or GET /payroll-summary for internal admin tools

3️⃣ Authentication/Authorization Services
Internal login or SSO APIs (Single Sign-On)
Example: POST /internal/auth/validateToken

4️⃣ Enterprise Applications
ERP systems (SAP, Oracle) exposing APIs to internal modules
Example: Inventory, procurement, and billing services communicating via APIs


• Composite APIs – 
Composite APIs combine multiple API calls into a single request, which is especially useful in microservices architectures.
Understanding the type of API is important because it affects authentication, security requirements, and the scope of testing.
eg.
Scenario: Book a trip with flight, hotel, and payment
You want to allow a client (like a mobile app or web app) to book a complete trip in one API call, instead of making three separate calls.
/////////////////////////////////////////////////////////////////////////////working//////////////////////
Step 1: Client Sends a Single Request
The client sends a POST request to the Composite API endpoint:

POST /composite-api/book-trip
Body:
{
  "flight": { "from": "NYC", "to": "LAX", "date": "2026-01-10" },
  "hotel": { "location": "Los Angeles", "nights": 3 },
  "payment": { "method": "credit_card", "amount": 1200 }
}
---------------------------------------------------------------------
Step 2: Server Receives the Request
The Composite API server acts like a conductor in an orchestra:
It parses the request and understands the three actions required:

Flight reservation
Hotel booking
Payment processing

It prepares internal API calls for each of these actions.
-----------------------------------------------------------------------
Step 3: Server Calls Multiple APIs Internally
Here’s what happens behind the scenes:
a. Flight API call

GET /flights?from=NYC&to=LAX&date=2026-01-10

Checks availability of flights.
Returns flight confirmation ID and seat info.

b.Hotel API call

POST /hotels/reserve
Body: { "location": "Los Angeles", "nights": 3 }


Reserves a hotel room.
Returns booking confirmation number.

c.Payment API call

POST /payments
Body: { "method": "credit_card", "amount": 1200 }

Processes the payment.
Returns payment transaction ID and status.

Note: These APIs can be of different HTTP methods (GET, POST) and even communicate with different backend systems.
-------------------------------------------------------------------------------------------------------------------
Step 4: Server Aggregates Responses
After all internal API calls complete, the Composite API server combines the results into a single response object:

{
  "flightConfirmation": { "flightId": "AB123", "seat": "12A" },
  "hotelConfirmation": { "bookingId": "H98765", "room": "Suite" },
  "paymentStatus": { "transactionId": "P123456", "status": "success" }
}
The client gets everything it needs in one response.
The client does not need to know that internally three APIs were called.

3. APIs by Purpose
🔹 Web APIs
Web APIs are application interfaces that are accessed over the internet using standard HTTP protocols.
They enable communication between different applications or services and are commonly used in platforms like social media, e-commerce, and cloud services.
UI → Web API HTTP Request → Server Validates & Processes → Web API Response → UI Updates

🔹 Library / Framework APIs
Library or framework APIs provide a set of functions and classes that developers can use within a programming language.
They are not network-based and are used to simplify coding tasks. 
Examples include the Java API and Python standard library. Collections API,File I/O API,Networking API

🔹 Operating System APIs
Operating System (OS) APIs allow applications to interact with the underlying operating system’s features, such as file systems, memory, and hardware.
Examples include the Windows API and the POSIX API.(Portable Operating System Interface)(Purpose:API for Unix-like operating systems (Linux, macOS, etc.))
ReadFile("C:\\Users\\Alice\\Documents\\file.txt", buffer, size, &bytesRead);
ReadFile("file.txt")

🔹 Hardware APIs
Hardware APIs allow software applications to communicate with and control hardware devices, such as cameras, GPS modules, and Bluetooth adapters.
Examples include Camera APIs, GPS APIs, and Bluetooth APIs.
a) Graphics / GPU API
OpenGL is a Graphics / GPU API.
Its purpose: Let programs draw shapes, images, 3D objects, and effects on the screen.
It communicates with the GPU (Graphics Processing Unit) so your CPU doesn’t have to do heavy rendering work.
b) Camera / Sensor API
Mobile devices expose hardware APIs for camera, GPS, accelerometer, etc.

4. APIs by Communication Pattern
🔹 Synchronous APIs
Synchronous APIs are those where the client sends a request and waits for the server to respond before continuing.
A common example is a REST API request.

🔹 Asynchronous APIs
Asynchronous APIs allow the client to send a request without waiting for an immediate response.
The response is handled later through callbacks, events, or message queues.
Examples include Webhooks and message queue systems.

4. Explain HTTP methods in API testing.

• GET – Retrieve data from the server.
• POST – Create new resources.
• PUT – Update a resource completely.
• PATCH – Update a resource partially.
• DELETE – Remove a resource.

HEAD 	 	Same as GET but returns only headers metadata (no body)
OPTIONS	 	when you want to know what actions are allowed on a resource before making the actual request.        
TRACE 	 	Use TRACE only for debugging to see how a request is modified as it travels through intermediaries—never for normal 		application logic             
CONNECT	 	Creates a tunnel (used for HTTPS via proxy)    
LINK	 	Establish relationship between resources       
UNLINK		Remove relationship between resources          


Example:
GET /users/1 – fetch user with ID 1
POST /users  - Create a new user
PUT /users/1 – update the entire user object
PATCH /users/1 – update only part of the user data
DELETE /users/1 - Delete user with ID 1
HEAD /users/1 - Get response headers (status, content-type) without body
OPTIONS /users/1 - Returns allowed methods like GET, PUT, PATCH, DELETE
TRACE /users/1 - Server echoes back the request (usually disabled for security)
CONNECT api.example.com:443 - Establish HTTPS tunnel through a proxy
LINK /users/1/groups/10 - Link user 1 to group 10
UNLINK /users/1/groups/10 - Remove user 1 from group 10

5. What is idempotency in HTTP methods?

Idempotency means sending the same request multiple times will result in the same outcome.
• GET, PUT, DELETE ,PATCH, HEAD , OPTION → Idempotent.
• POST → Not idempotent.
Example:
• PUT /user/1 { "name": "John" } → No matter how many times you send it, result remains the same.
• POST /user { "name": "John" } → Multiple sends will create multiple users.
POST /users
First call → creates user A
Second call → creates user B
❌ Different results

eg.
Charging a user $50 for an order.
Challenge: Network fails after first request → client retries.
Solution: Use Idempotency Key (unique token per request).
Behavior:

First request → charges $50.

Retry with same idempotency key → no extra charge; the original response is returned.

Idempotency is crucial whenever operations can be retried or executed multiple times due to failures, network issues, or distributed architectures. 
It prevents unintended effects like duplicates, extra charges, or inconsistent state.

6. Difference between URI, URL, and Endpoint.
• URI – Identifier for a resource (more general).
• URL – A type of URI that includes the location (e.g., protocol + domain + path).
• Endpoint – Specific URL where an API resource can be accessed.
Example:
• URI: /users/123
• URL: https://api.example.com/users/123
• Endpoint: GET request to that URL.

eg.
https://www.example.com:443/path/page.html?query=test#section1

https → protocol
www.example.com  host
443 → port
/path/page.html → path to resource
?query=test → query parameters
#section1 → fragment (not used in API testing only for UI knowledge)

8. What are headers in API requests and responses?
Headers carry metadata — such as authentication tokens, content type, caching instructions.
that tells the client and server how to communicate, process data, and apply rules correctly.
Examples:
• Content-Type: application/json
• Authorization: Bearer <token>
• Accept-Language: en-US

1. They Control How Data Is Interpreted

Headers tell the receiver what kind of data is being sent and how to handle it.
Examples:

Content-Type: application/json → tells server/client the body is JSON
Content-Encoding: gzip → tells data is compressed

📌 Without headers, the receiver may misinterpret the data.
-----------------
2. They Enable Client–Server Communication Rules

Headers define expectations and capabilities between client and server.
Examples:
Accept: application/json → client says what formats it can accept
Accept-Language: en-US → preferred language

📌 This enables content negotiation.
---------------
3. They Carry Authentication & Authorization Data

Headers securely send identity and access information.
Examples:
Authorization: Bearer <token>
Cookie: session_id=abc123

📌 Without headers, secure APIs and sessions cannot work.
----------------
4. They Improve Performance

Headers help with caching, compression, and connection reuse.
Examples:
Cache-Control: max-age=3600
ETag / If-None-Match
Keep-Alive

📌 This reduces bandwidth usage and speeds up applications.
-----------------
5. They Support Idempotency & Reliability

Headers help prevent duplicate or unsafe operations.
Examples:
Idempotency-Key: xyz-123
Retry-After: 120

📌 Critical for payments, retries, and distributed systems.
----------------
6. They Provide Status & Debug Information

Response headers give extra context about the server’s behavior.
Examples:
X-Request-ID → trace requests
Server: nginx
Date
-------------------
📌 Essential for monitoring and debugging.

7. They Enable Security Features
Headers protect against common web attacks.
Examples:
HTTPS related headers
Content-Security-Policy
X-Frame-Options
Strict-Transport-Security

📌 Without security headers, apps are vulnerable.

9. What is JSON and why is it preferred over XML?
JSON (JavaScript Object Notation) is lightweight, easy to read, and natively supported by JavaScript.
Compared to XML:
• Smaller payloads.
• No closing tags → faster parsing.
• More readable for humans.
{
  "productId": 101,
  "name": "Wireless Mouse",
  "category": "Electronics",
  "price": 29.99,
  "stock": 120,
  "ratings": 4.5
}
VS
<product>
  <productId>101</productId>
  <name>Wireless Mouse</name>
  <category>Electronics</category>
  <price>29.99</price>

  <ratings>4.5</ratings>
</product>

14. What are environments in Postman?

Environments in Postman are sets of variables used to manage different API configurations like dev, staging, and production. 
They allow us to parameterize values such as base URLs, tokens, API keys, or user IDs. 
By switching environments, the same request can run against different systems without modifying the request itself. 
This makes API testing reusable, maintainable, and safer when working across multiple deployments.

16. What is the difference between Pre-request Script and Tests in Postman?

Pre-request scripts run before the API request to prepare dynamic data or authentication, while Tests run after the response to validate the API behavior and extract values for subsequent requests.

Purpose:
Prepare data required for the request
Set or update environment/collection variables
Generate dynamic values

Common Use Cases:
Generating authentication tokens
Creating timestamps
Generating random test data
Encrypting request payload

//pre-request eg:
1️⃣ Generating Authentication Tokens
Example: Create a Basic Auth token using Base64 encoding.

let username = "testuser";
let password = "test123";
let token = btoa(username + ":" + password);
pm.environment.set("auth_token", token);

Then use it in the header:
Authorization: Basic {{auth_token}}
📌 Use case: APIs that require Basic Authentication.

2️⃣ Creating Timestamps
Example: Generate a current timestamp.

let timestamp = new Date().toISOString();
pm.environment.set("timestamp", timestamp);

Example output:
2026-03-08T10:30:45.123Z
Use in request body:
{
  "transaction_time": "{{timestamp}}"
}
📌 Use case: Banking APIs often require transaction timestamp.

3️⃣ Generating Random Test Data
Example: Generate a random email and number.

let randomNum = Math.floor(Math.random() * 10000);
let email = "testuser" + randomNum + "@mail.com";
pm.environment.set("random_email", email);

Use in request:
{
  "email": "{{random_email}}"
}
📌 Use case: Avoid duplicate data during user registration testing.

4️⃣ Encrypting Request Payload
Example: Encrypt payload using CryptoJS (SHA256).

let payload = "account=12345&amount=5000";
let encrypted = CryptoJS.SHA256(payload).toString();
pm.environment.set("encrypted_payload", encrypted);

Example header/body:
X-Signature: {{encrypted_payload}}
📌 Use case: Secure APIs like payment or banking transactions.

Difference Between Pre-request Script and Tests in Postman
1️⃣ Pre-request Script
Definition:
Pre-request scripts contain JavaScript code that executes before the API request is sent to the server.

Purpose:

Prepare data required for the request

Set or update environment/collection variables

Generate dynamic values

Common Use Cases:

Generating authentication tokens

Creating timestamps

Generating random test data

Encrypting request payload

Example

// Generate timestamp
pm.environment.set("timestamp", Date.now());
Another example (token generation):

pm.environment.set("authToken", "12345abcde");
These values can then be used in the request.

2️⃣ Tests
Definition:
Tests are JavaScript scripts that execute after the response is received from the server.

Purpose:

Validate API responses

Verify response structure, data, and status codes

Store response values for future requests

Common Use Cases:

Verify status code

Validate response body

Check response time

Extract tokens or IDs for next request

Example

pm.test("Status code is 200", function () {
    pm.response.to.have.status(200);
});
Extract value example:

let jsonData = pm.response.json();
pm.environment.set("accountId", jsonData.accountId);
Key Difference
Feature	Pre-request Script	Tests
Execution Time	Before request	After response
Purpose	Prepare request data	Validate response
Example	Generate token	Check status code
✅ Senior-level one-line answer

Pre-request scripts run before the API request to prepare dynamic data or authentication, while Tests run after the response to validate the API behavior and extract values for subsequent requests.

How do you send authentication credentials in Postman?
Authentication credentials in Postman can be sent using the Authorization tab, headers, or request body, depending on the API’s authentication mechanism.

1️⃣ Using Authorization Tab (Recommended)
Postman provides a built-in Authorization tab where you can select the authentication type and provide credentials.

Common types include:

Basic Auth

Bearer Token

API Key

OAuth 2.0

Digest Auth

Example – Bearer Token

Authorization → Type: Bearer Token

Token: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Postman automatically sends it in the header:

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
2️⃣ Using Headers
Credentials can also be manually sent through HTTP headers.

Example:

Authorization: Bearer abc123xyz
Or API key:

x-api-key: 123456789
3️⃣ Using Request Body
Some APIs require credentials in the request body, typically during login.

Example:

POST /login

{
  "username": "rahul",
  "password": "password123"
}
The server then returns an access token used for subsequent requests.

4️⃣ Using Environment Variables
For automation and security, credentials like tokens or API keys are usually stored in environment variables.

Example:

Authorization: Bearer {{authToken}}
This allows the same request to run across different environments (dev, QA, prod).

Senior-Level Summary

59. How do you retry failed requests in Postman scripts?
Postman itself doesn’t have automatic retries, but you can simulate:
++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++

In Postman, failed requests can be retried using postman.setNextRequest() with a retry counter stored in variables.
If a request fails (for example status code ≠ 200), the script increments the retry count and re-runs the same request until the maximum retry limit is reached.

Example Script
let retryCount = pm.environment.get("retryCount") || 0;

if (pm.response.code !== 200 && retryCount < 3) {
    retryCount++;
    pm.environment.set("retryCount", retryCount);
    postman.setNextRequest(pm.info.requestName); 
} else {
    pm.environment.set("retryCount", 0);
}

//
What this script does

1️⃣ Gets retry count

let retryCount = pm.environment.get("retryCount") || 0;

If no retry value exists, it starts from 0.

2️⃣ Checks if request failed

pm.response.code !== 200

3️⃣ Retries the request

postman.setNextRequest(pm.info.requestName);

Runs the same request again.

4️⃣ Stops after 3 retries

retryCount < 3

5️⃣ Resets retry counter when success occurs

Missing token → Should not allow access

XSS payloads (<script>alert(1)</script>)

Passwords

Credit card details
Internal server errors or stack traces

we analyze the CI pipeline logs where Newman outputs request, response, and assertion details.
These logs help us identify whether the failure is due to authentication, environment configuration, test data, or backend issues.
and Retry manually in Postman to isolate the issue.

POST /api/orders
//API CI-CD test fail output response:

✔ Login API Test - Passed
✔ Get Products API Test - Passed
✖ Create Order API Test - Failed

Reason:
Expected: 201
Received: 500

Response Time: 3245ms
//500:It means the server tried to process your request but something broke on the server, and it couldn't complete it.
------------------------------------------------------
When an API test fails in CI/CD, I first analyze the failure output like status code, error message, and logs.
For example, if a Create Order API expected 201 but returns 500 with "Database connection failed", I know the issue is backend or infra — not test logic.
Based on failure type (401, 404, 500, timeout), I narrow down whether it's auth, config, data, or dependency issue.

When pipeline runs:
CI (Jenkins / GitHub Actions / GitLab)
        ↓
Runs Newman command
        ↓
Newman executes Postman tests
        ↓
Outputs logs to CI console
        ↓
Build fails if assertions fail

So you're still checking Newman results…

…but through CI logs.

Example Real-time “Add to Cart” flow (API + UI):
1️⃣ User clicks “Add to Cart” (UI)

User is logged in
UI sends an API request to the backend
Endpoint: POST /cart/add
{
  "productId": "P123",
  "quantity": 1
   //optional session/token
}
Request validation:
Check required fields and data types
Reject malformed requests → return 400 Bad Request

2️⃣ API checks User Authentication

API verifies:
Validate JWT / session token
Ensure user exists and is active
Check permissions (e.g., guest users may have restricted access)
❌ If not authenticated → return 401 Unauthorized

3️⃣ API checks Stock Availability /Stock Availability Check

Query inventory service / database for requested product and quantity :
Is product in stock?
Is requested quantity available?
reserved stock/ Optionally lock the stock (pessimistic) or mark it reserved ?
❌ If out of stock → return 409 Conflict
{
  "message": "Product out of stock"
}

4️⃣ API checks Pricing & Discounts Validation 

Fetch current price from product catalog
Apply:
Discounts
Offers
Taxes (if needed)
Verify that the price matches business rules to prevent client-side tampering
Failure → return 400 Bad Request / 422 Unprocessable Entity
//👉 Prevents UI price tampering

5️⃣ API adds item to cart (Transaction)

Begin a database transaction (optional: use ACID compliance for reliability)
Insert or update the cart table with the product and quantity
Update reserved stock if applicable
Commit transaction
Rollback if any step fails to ensure atomicity

All checks pass → item added
Cart updated in database
Stock reserved (optional)

6️⃣ API sends response to UI
{
  "status": "success",
  "cartCount": 3,
  "price": 999,
  "message": "Product added to cart"
}

7️⃣ UI updates in real time

Cart icon count updates
Price displayed
Success message shown
👉 UI only displays what API confirms
