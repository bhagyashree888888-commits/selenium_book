Q. What is Software Testing? 

Software Testing is the process of evaluating and verifying that a software application or system meets the specified requirements and works as intended. 
It involves executing the software to identify defects, ensuring it is free from critical bugs, and confirming that it delivers the expected business value. 
• The main goals are: 
o Verification: Does the software meet the design specifications? 
o Validation: Does the software meet the customer’s needs? 
• Testing is not only about finding defects; it’s also about preventing defects and improving quality.

UAT is recommended but not mandatory. In some Agile or product-based projects, QA testing and product owner approval replace formal UAT.

 => Several Key Aspects of Software Maintenance

Voting System – Waterfall SDLC
(How each phase works & overall workflow)

Voting systems are highly regulated, security-critical, and audit-driven, which is why Waterfall (or a very strict V-Model) is still used.

1️⃣ Requirement Analysis Phase
Government / Election Commission defines fixed requirements
Legal, security, and compliance rules are finalized
Requirements are frozen early (very important)

Examples of requirements
One voter → one vote
Voter authentication must be mandatory
Votes must be anonymous
System must not allow vote modification
Audit logs must be tamper-proof
QA role :Review requirement documents
Check for:Missing scenarios , Security gaps , Edge cases (power failure, network failure), Ensure requirements are testable
📌 No coding starts until requirements are signed off.

2️⃣ System Design Phase
Architects design:
System architecture
Database schema
Security mechanisms (encryption, access control)
Hardware + software interaction (EVM, servers)

Example : Separate modules for:
Voter authentication
Vote casting
Vote storage
Result counting

QA role :
Review design documents
Understand data flow
Identify test points
Prepare high-level test scenarios
📌 QA starts planning tests here (V-Model thinking).

3️⃣ Development Phase
Developers implement code strictly based on design
Each module is developed separately
Unit testing by developers
Example modules :
Login & authentication module
Vote recording module
Encryption module
Result calculation module

QA role : No execution yet (mostly)
Prepare: Detailed test cases , Test data ,Traceability matrix (RTM)
📌 Changes are discouraged at this stage.

4️⃣ Testing Phase (Main QA Phase)
QA executes testing after full development is complete.
Types of testing done : Functional testing , Security testing , Integration testing ,System testing ,Performance & load testing, Failover & recovery testing ,Compliance testing
                     User Acceptance Testing (UAT)
QA examples :
Verify vote count accuracy
Ensure duplicate voting is blocked
Test system under high load (election day traffic)
Validate audit logs
Check data encryption
Defect handling
Defects logged
Fixed by dev
Retested by QA
Regression testing performed
📌 This phase is long and very detailed.

5️⃣ Deployment Phase
System is deployed in a controlled environment
Often deployed in phases (pilot → full rollout)
Strict approval required

QA role :
Support deployment verification
Perform smoke tests
Validate environment readiness

6️⃣ Maintenance Phase :
Bug fixes (if any)
Security patches
System monitoring
Minor updates (very controlled)

QA role :
Verify fixes
Perform regression testing
Ensure no impact on core voting logic
End-to-End Workflow (Simple)

No overlapping phases. Each phase must be completed and approved before moving to the next.

Why Waterfall suits Voting Systems (Interview MUST)

✔ Requirements are fixed by law
✔ Changes are risky and expensive
✔ Heavy documentation required
✔ Strong audit & compliance needs
✔ Security is critical
✔ Predictable timeline needed
Interview-
“Voting systems typically follow the Waterfall SDLC because requirements are fixed, legally regulated, and security-critical. Each phase is completed sequentially with strict reviews, ensuring accuracy, auditability, and compliance before moving forward.”

• Spiral Model

The exact number of loops of the spiral is unknown and can vary from project to project. 
Each loop of the spiral is called a phase of the software development process.

🧠 Example: Good for safety-critical systems like healthcare or automotive.

| **Activity**                               | **Description**  
                                                                                                                                                       
| **1. Planning**                            | Identify objectives, alternatives, and constraints for the current phase. 
					       Includes project planning, resource estimation,scheduling, and defining system requirements. 


| **2. Risk Analysis (Risk Assessment)**     | Analyze and identify potential risks, uncertainties, or problems that could affect the project.
 					       Evaluate alternatives and develop strategies to mitigate those risks.   


| **3. Engineering (Development & Testing)** | Design, develop, and test the product for that iteration. 
					      This may involve prototyping, coding, and verifying the features defined during the planning phase.           

| **4. Evaluation (Customer Review)**        | Present the developed product or prototype to the customer for feedback and evaluation. 
                                               The customer’s feedback is then used to plan the next spiral (iteration).       

🔎 When Spiral Model is Best Used?
✔️ Large systems ( defense, aerospace,Battlefield Communication System (Secure Military Network))
✔️ High-risk software (safety-critical apps, AI systems)
✔️ Projects where requirements evolve over time
✔️ Projects requiring regular customer feedback 
1️⃣ Defense Systems
Missile guidance software
Radar & surveillance systems
Command-and-control systems
3️⃣ Aerospace & Defense (R&D / New Technology)
Space exploration software (prototype phase)
Defense simulation systems
5️⃣ Defense Command & Simulation Systems
War-game simulation software(russia-ukrain)
Military training simulators
Command decision-support systems

spiral vs waterfall method :

| Feature / Point              | **Spiral Model**                               | **Waterfall Model**                                |
| ---------------------------- | ---------------------------------------------- | -------------------------------------------------- |
| **Development Type**         | Iterative & Risk-driven                        | Linear & Sequential                                |
| **Flexibility**              | Very flexible (changes allowed anytime)        | Very rigid (changes hard after development starts) |
| **Customer Involvement**     | High – client involved in every loop           | Low – client involved mainly at start & end        |
| **Risk Handling**            | Excellent – early risk analysis in every phase | Poor – risks found late, if at all                 |
| **Project Size Suitability** | Large, complex, long-term, high-risk projects  | Small, simple, well-defined projects               |
| **Cost & Time**              | More expensive & time-consuming                | Less costly & faster for small projects            |
| **Documentation**            | Moderate to high (depends on loops)            | Very high – every phase documented                 |
| **Working Product**          | Delivered in parts (prototypes / versions)     | Delivered only at the end                          |
| **Changes in Requirements**  | Easy to include new changes                    | Very difficult to include after design phase       |
| **End of Project**           | No fixed end – depends on number of spirals    | Fixed and predefined end                           |
| **Best For**                 |  aerospace, AI, large systems                  | Simple apps, static websites, student projects     |

• Prototype Model
SDLC approach where an early working model / simplified model / mock-up of the software  is built to collect user feedback and refine requirements before full development starts.
Shows basic features, screens, or workflows to refine their expectations.

The prototype model is used whenever building the full system first is too costly, risky, or uncertain. It allows testing, validation, and feedback before large-scale investment.

Prototype Model Flow:
1. Collect Requirement  2. Build Quick Prototype  3. User Evaluates Prototype  4. Modify Prototype Based on Feedback
5. Repeat Until Approved  6. Develop Final System

Smart City Traffic Management – Prototype Model (Easy Version)


1️⃣ Requirements Gathering – What do we want?
Decide what the system should do.(stakeholders like city officials,traffic police,engg basic goal defined)
Example: Show traffic congestion, alert jams, and suggest alternative routes.Give emergency vehicles green signals,Monitor traffic in real time.
Simple action: Draw a simple sketch of a dashboard with roads colored green/red for traffic.

2️⃣ Quick Design – Make a small test version
Build a small working version to see if the idea works.
Example: Use 2–3 main roads and simulate traffic with dummy data.Basic idea of how sensor data will appear on screen of traffic
Purpose: Check how the dashboard looks and works before building the whole system.Initial design blueprint.

3️⃣ Implementation – Make it work
Build a working prototype with real or simulated sensors.
Example: Dashboard updates traffic status in real time. Road A = red (busy), Road B = yellow (slow).
Purpose: See the system working in action, not just a sketch.Buttons to change traffic light timing.

4️⃣ Evaluation & Feedback – Ask users what they think
Show the prototype to city managers or test users.
Example: Managers say “We need traffic predictions for the next 30 minutes.”
Purpose: Find problems early so we can improve.

5️⃣ Refinement – Make improvements
Fix problems and add new features based on feedback.
Example: Add predicted traffic alerts, suggest alternate routes, improve dashboard colors.
Purpose: Make the system better before full deployment.

6️⃣ Deployment – Launch full system
Connect all real sensors and cameras for the entire city.Real sensors, cameras, and networks are integrated.Deployed first in a small city area, then city-wide.
Example: Live traffic updates for all roads, alerts sent to citizens’ apps.
Benefit: Because we tested with a prototype first, the system works correctly and safely.

• V & V Model

Q . Difference between Verification and Validation. 
• Verification ensures the product is built according to the requirements and design. 
It answers, “Are we building the product right?” 
Example: Reviewing documents, inspecting code. 

1.Reviewing requirement documents to ensure:
Tax calculation rules match government regulations
Discount logic follows store policies

2.Checking database design to confirm:
Inventory tables correctly track stock levels
Customer tables include loyalty points fields

3.Code reviews to ensure:
POS billing module follows the defined algorithm
Security standards are applied to payment modules

• Validation ensures the product meets the actual needs of the user. 
It answers, “Are we building the right product?” 

Product Master :
New products added appear correctly on POS and website
Price, tax, and barcode updates reflect instantly during checkout
Product availability updates correctly after every sale
Sales reports generate correctly by store, product, and date
Inventory reports update accurately after each sale or purchase
Promotion performance reports reflect correct discount usage
//POS here :
✔ POS is offline / in-store
✔ Cashier scans product : Stock quantity decreases 
✔ Sale updates admin panel
✔ Reports are generated

Example: Testing the application with real-world scenarios. 
Key point: Verification is a static process (no code execution), while Validation is a dynamic process 
(involves running the code).

• Hybrid Model
In this model, some phases may follow a sequential approach for stability (like requirement analysis and design), 
while development and testing may follow iterative cycles to deliver faster feedback and improvements.
The main goal of the Hybrid Model is to leverage the strengths of each model while minimizing their weaknesses, ensuring both quality and adaptability.

1. Requirements Gathering (Prototype Iterations)

Meet users (doctors, nurses, admins, patients) to gather requirements.
Build initial UI prototypes — simple screens showing how the system will look and behave.
Collect feedback from users.
Refine and modify the prototype multiple times until the requirements are confirmed.
Ex:
A prototype of the appointment scheduling system is created. 
Doctors review it and 
suggest adding “patient history” visibility on the same screen. 
The design is updated before development begins.

2. System Design (V-Model)

Create high-level and detailed design documents.
Define data flow, system architecture, and module interactions.
Plan test cases for each design phase (as per the V-Model’s “Verification” side).
Map each requirement to a corresponding validation step.
Ex
Designing how data flows from patient registration → doctor consultation → billing → pharmacy while maintaining data security (HIPAA compliance : Health Insurance Portability and Accountability Act).

3. Module Design & Coding (V&V – Verification)

Break the system into smaller modules (e.g., Billing, Pharmacy, Doctor Scheduling).
Write code for each module based on the design.
Perform unit testing for each module to verify it works as expected.
Ensure code meets software quality standards.
Ex:
Develop the Billing Module — ensure it correctly calculates charges, taxes, and generates invoices. Unit testing verifies each function works properly.

4. Integration & Validation (V&V – Testing Phases)

Combine all verified modules (integration).
Perform integration testing to ensure modules interact correctly.
Conduct system testing to check the entire application workflow.
Validate that all requirements (defined from prototype phase) are satisfied.
Ex:
Integrate the Patient Registration, Appointment, and Billing modules. Validation confirms that when a patient registers and visits a doctor, billing and record updates happen automatically.

5. User Evaluation (Prototype)
Conduct User Acceptance Testing (UAT) sessions.
Users test the system with real scenarios.
Collect user feedback for usability or design improvements.
Refine user interfaces or small features using prototype iterations again.
Example (HMS):
Nurses and doctors use the system in a test environment. 
They suggest increasing text size on patient dashboards and adding a “search by patient ID” shortcut — changes are made before go-live.

6. Deployment & Maintenance
Deploy the application in the hospital’s live environment.
Train end-users (staff, doctors, receptionists).
Monitor the system and fix any bugs reported.
Continuously gather feedback and make minor improvements through small prototypes or patches.
Example (HMS):
After deployment, hospital staff use the system daily. Later, an update adds a new “Digital Prescription” module developed and tested using the same V&V + Prototype cycle.

For lessons learned, I document issues faced during testing, root causes of defects, process gaps, and suggestions for improvement. I compile these in a lessons learned report or test closure document, and share them with the team to improve future testing efficiency and quality.

Q. What is Test Case? 
A Test Case is a set of conditions and steps that determine whether a software feature works as expected. 
Includes: Test Case ID, description, preconditions, steps, expected result, actual result, status. 
Example: Test the “Forgot Password” feature—steps include entering an email, checking if a reset link is 
received. 
----------------------------------------------------------------------------------------------------------------
Test Scenario :

A Test Scenario is a high-level description of what to test. It outlines what functionality or feature needs to 
be validated without going into detailed steps. 
• Focuses on user journeys rather than step-by-step execution. 
• Useful when we want to ensure end-to-end coverage. 
Example: 
For an e-commerce site: 
Scenario – Verify that a user can place an order successfully. 
This scenario will cover login → searching → adding to cart → payment → order confirmation.

What are Test Design Techniques?
 
Test Design Techniques are systematic approaches to creating test cases that ensure maximum coverage with minimum effort. 
They help testers focus on critical areas, avoid duplication, and discover more defects. 
They are generally divided into: 
1. Black-Box Techniques – Based on requirements, without looking at the code. 
2. White-Box Techniques – Based on code structure. 
3. Experience-Based Techniques – Based on tester’s knowledge and experience. 
	a.Error guessing: prone area is guessed by experience tester based on this prior experience of same type of application.
Example: If a login page requires a password of 8–12 characters, you can use Boundary Value Analysis to 
check passwords of 7, 8, 12, and 13 characters. 
------------------------------------------------------------------
Boundry value analysis :
 
BVA focuses on testing at the edges of input ranges, as defects often occur at boundaries. 
Example: 
If the valid input is 18–60 for age: 
Test values: 17 (just below), 18 (minimum), 60 (maximum), 61 (just above). 
This ensures that both lower and upper limits are tested, along with just-outside values. 
eg.A bank allows ATM withdrawals between ₹100 and ₹50,000 per transaction.

 99    101(min+-1)                         49999     50001

Equivalence partitioning :

Equivalence Partitioning divides test data into groups (partitions) that are expected to be treated the same by 
the system. If one value in a group works, all should work; if one fails, all fail. 
Example: 
Suppose a field accepts numbers from 1 to 100. 
Partitions: 
• Valid: 1 to 100 (e.g., test with 50) 
• Invalid: < 1 (e.g., 0) and > 100 (e.g., 101) 
Benefit: Reduces the number of test cases without losing coverage. 

---------------------------------------------------------------------------------
Decision Table Testing : 
Decision Table Testing is used for systems with complex business rules. It helps ensure all possible 
combinations of inputs and outcomes are tested. 
Example: Loan approval: 
Conditions: 
1. Credit score > 700 
2. Income > ₹30,000 
   Actions: Approve / Reject

State Transition Testing  : 
State Transition Testing checks how the system behaves when changing from one state to another based on 
events/inputs. 

Example: ATM machine: 
• State: Card inserted → Enter PIN → Valid PIN → Access account. 
• Test invalid PIN thrice → State changes to “Card blocked.” 
Used when the software has finite states and rules for transitions. 
---------------------------------------------------------------
Error Guessing :

Error Guessing relies on the experience and intuition of the tester to guess where defects are likely to be. 
• Not a formal technique. 
• Often used alongside other methods. 
Example: A tester may guess that an email field might accept invalid formats like test@.com and try those 
inputs.

Q. Defect Life Cycle
The Defect Life Cycle (Bug Life Cycle) describes the stages a defect goes through from discovery to closure.

                new   ;scrum master validate

Typical stages: 
1. New: Tester logs the defect. 
2. Assigned: Defect is assigned to a developer. 
3. Open: Developer starts working on it. 
4. Fixed: Developer fixes the defect. 
5. Retest: Tester retests to verify the fix. 
6. Closed: Defect is confirmed fixed. 
7. Reopened: If the defect reappears. 
Example: 
You find the payment button unresponsive → log it → dev fixes → you retest → if working fine, you close it.

Q. What is Compatibility Testing? 
Compatibility Testing ensures the application works across different devices, browsers, operating systems, and 
network environments. 
Example: Checking if a travel booking site works on Chrome, Firefox, Safari, and Edge on both Windows and  Mac.              

Types of Compatibility Testing by Application Type
1. Web Application
Test the website on multiple browsers and versions (e.g., Chrome, Firefox, Edge, Safari).
Verify it works across different operating systems (Windows, macOS, Linux).
Check responsive behavior on different screen resolutions and devices (desktop, tablet, mobile).
Example:
✅ Check if the online banking portal displays correctly in Chrome (Windows), Firefox (Ubuntu), and Safari (macOS).

2. Client-Server Application
Verify compatibility between different client configurationhos and the server environment.
Test how the application behaves with varied network speeds, different OS versions, and database servers.
Example:
✅ Test a banking client app installed on Windows 10 and Windows 11 connecting to the same core banking server.

3. Stand-Alone Application
Ensure installation and performance are consistent.
Example:
✅ Test a loan calculator desktop app on Windows 8, 10, and 11 with different screen resolutions.

🌐 Cross-Platform Compatibility Scenarios
a. Multiple Browsers on One OS
Test the web app in Chrome, Edge, Firefox, Safari — all on the same OS (e.g., Windows 11).
Purpose: Verify consistent UI/UX and functionality across browsers.
Example:
✅ Banking login and fund transfer pages behave identically in all browsers on Windows.

b. Multiple OS on One System
Using virtual machines or containerization tools (like VMware, Docker), run different OS on one system and test the app.
Purpose: Validate the application’s stability and look/feel on multiple operating systems.
Example:
✅ Test banking web portal on Windows 11, Ubuntu, and macOS (same hardware via VMs).

Q. What is Performance Testing? 
Performance Testing checks the speed, responsiveness, and stability of a system under expected workloads. 
• Identifies bottlenecks and ensures performance goals are met. 
Example: Testing if a banking site loads the account summary within 3 seconds for 500 concurrent users.

checks how a system behaves when it is subjected to a specific expected load

What is Stress Testing? 

break point of server, stability , extreme traffic
how a system behaves under extreme or beyond-normal load conditions

Suppose a banking system normally handles 2,000 concurrent users.
In stress testing, you gradually increase the load to 5,000 or 10,000 users to see what happens:
Does the app crash or slow down?
Does it throw proper error messages like “Server Busy”?
Can it recover once load returns to normal?

✅ The system should slow down but not lose data or crash permanently. It should recover automatically when the load decreases.

Q. What is Soak Testing / Endurance Testing / Stability Testing?
Running a system at high load for a prolonged period of time to identify the 
performance problems is called Soak Testing.
testing an online banking system:
You simulate 500 concurrent users continuously performing transactions (balance checks, transfers, logins)
Run the test for 48 hours non-stop
During this time, you monitor:
Memory usage (does it keep increasing?)
CPU utilization (does it stabilize or stay high?)
Response time (does it get slower over time?)
Any crashes or database disconnections

✅ The system should remain stable, responsive, and consistent throughout the test period — no memory leaks or slowdowns.
 Running a live video stream for 72 hours to ensure no memory leaks or crashes.

Q.What is Spike Testing
online banking site normally handles 1,000 users.
During Spike Testing, you simulate:
A sudden jump from 1,000 to 5,000 users in a few seconds (e.g., salary day).
After some time, reduce it back to 1,000 users again.
You observe:

Does the system crash or slow down when load spikes?
Does it show proper error messages (e.g., “Server busy”)?
How fast does it recover when load returns to normal?

✅ The system might slow briefly but should not crash — and should recover automatically when load decreases.

Q. What is Smoke Testing  /Dry Run? Why is it called so? 

Smoke Testing is a preliminary check to verify that the most critical functionalities of an application work 
before conducting more detailed testing. 
• Also known as Build Verification Testing (BVT). 
• Ensures the application is stable enough for further testing. 
Example: In an e-commerce app, smoke testing might include logging in, searching for a product, adding to cart, and logging out. 
Why called “Smoke Testing”? In hardware testing, if a device smoked after powering on, it failed the initial test. 
The software analogy means, “If the build fails basic tests, it’s not worth continuing.”

Q.What is Regression Testing?

Regression Testing ensures that new changes (code updates, bug fixes, enhancements) have not broken existing 
features. 
• It’s repeated after every change in the application. 
• Often automated for efficiency. 
Example: If a payment gateway’s UI is updated, regression testing ensures that login, search, cart, and other 
existing features still work. 

+++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++++
1. New functionalities are added to the application
2. Change Requirement (In organizations, we call it as CR)
3. Defect Fixing
4. Performance Issue Fix
5. Environment change (E.g., Updating the DB from MySQL to Oracle)

o Unit Regression testing :usually a single module or feature where the change happened.
Developer fixed a bug in the “Interest Calculation” logic inside the Loan Module.
✅ Tester performs unit regression only on:
The Loan calculation screen
The interest formula validation
No need to test login, fund transfer, etc. — only that specific module

o Regional Regression testing :group of related modules (region) that are functionally connected to the changed module
Fund Transfer (main change area)
Account Balance Update
Transaction History
Notifications (SMS/Email)
These are related features — all may be affected by the change

o Full Regression testing:entire application end-to-end to ensure no part of the system is broken by recent changes
Login & Authentication
Account Summary
Fund Transfer
Loan, Cards, Investments
Reports, Notifications, etc.

Q. What is Exploratory Testing? How is it different from Ad-hoc Testing? 

Exploratory Testing is simultaneous learning, test design, and execution without pre-written test cases. 
• Done by experienced testers to uncover unexpected defects. 
Difference: 
• Exploratory: Structured with a charter (goal). 
• Ad-hoc: Completely unstructured and random. 
Example: While exploring a social media app, a tester tries unusual profile names or long status updates to see 
if the system handles them.

Q . What is the purpose of Test Documentation? 

Test documentation serves as a knowledge base for the testing process, ensuring that testing is structured, 
traceable, and repeatable. 
Its main purposes are: 
• To communicate testing scope, approach, and progress to stakeholders. 
• To provide evidence that testing was carried out. 
• To help in knowledge transfer to new team members. 
• To track coverage and ensure all requirements are tested. 
Examples of Test Documentation: 
• Test Plan 
• Test Cases 
• Test Scenario Documents 
• Traceability Matrix 
• Test Summary Report

Q . What are Entry and Exit Criteria in Testing? 

• Entry Criteria: Conditions that must be met before testing begins. 
Example: Test environment ready, test data prepared, build deployed. 
• Exit Criteria: Conditions that must be met before ending testing. 
Example: All planned test cases executed, critical defects fixed, test summary report prepared.

• Scope of testing 
• Test execution results 
• Defect details and their status 
• Coverage analysis 
• Risks and recommendations

Q. What is Use Case Testing? 
Use Case Testing is based on user scenarios describing how the system will be used in real life. 
• Focuses on end-to-end workflows. 
• Helps find gaps in integration points. 
Example: E-commerce: A “Place Order” use case will include login, product selection, adding to cart, 
payment, and confirmation.
==========================================================================================
Q.What is Pairwise Testing? 
Pairwise Testing is a combinatorial technique where testers create test cases covering all possible pairs of 
input parameters. 
• Reduces the total number of test cases while covering important interactions.
Example: 
Browser (Chrome, Firefox, Edge) × OS (Windows, Mac, Linux) → Instead of testing all 9 combinations, 
pairwise covers each pair at least once.

Q. What is Defect Leakage? 
Defect Leakage happens when a bug escapes from one testing phase and is found in a later stage. 
Example: A bug missed during system testing but found during UAT. 
------------------------------------------------------------------------------------------
Q. What is Defect Density? 
Defect Density = Number of confirmed defects / Size of the software module. 
It helps measure the quality of code. 
Example: 10 defects found in 500 lines of code → Density = 0.02 defects per LOC.
------------------------------------------------------------------------------------------
Q . What is Defect Clustering? 
Defect Clustering means that most defects are found in a small number of modules due to high complexity or 
poor design. 
Example: 80% of bugs being in the payment gateway module. 
-----------------------------------------------------------------------------------------
Q. What is a Bug Triage? 
Bug Triage is a meeting to prioritize and assign defects based on severity, priority, and business impact. 
-----------------------------------------------------------------------------------------
Q . What is a Showstopper Defect? 
A showstopper is a critical defect that blocks testing progress. 
Example: Application crashes immediately after login. 
-----------------------------------------------------------------------------------------
Q . What is a Latent Defect? 
A defect that exists but is not detected during testing and appears later under specific conditions. 
Example: A bug in a tax calculation system that only appears at year-end. 
----------------------------------------------------------------------------------------
Q . What is a Masked Defect? 
A defect hidden by another defect. 
Example: A crash in the payment page hides a bug in the discount calculation. 
-----------------------------------------------------------------------------------------
Q .  What is Root Cause Analysis (RCA)? 
RCA identifies the underlying cause of a defect to prevent recurrence. 
Example: Investigating why a login bug occurred → Found incorrect password hashing logic. 
-----------------------------------------------------------------------------------------

Q.Defect Tracking Tool : JIRA
Tool is software used to log, track, manage, and report defects (bugs) or issues in a system or application

Example in JIRA:
Defect Logged: QA tester logs a defect after finding a bug.
Triage / Review: Team reviews defect, sets priority and severity.
Assignment: Assigned to a developer for fixing.
In Progress: Developer works on fixing the bug.
Resolved: Developer marks the defect as resolved.
Testing / Verification: QA retests the defect.
Closed: If the defect is fixed and verified, it is closed.

4. What are the principles of Software Testing? 
1. Testing shows presence of defects 
2. Exhaustive testing is impossible

6. Testing is context depending

5. What is Exhaustive Testing? 
Testing all the functionalities using all valid and invalid inputs and preconditions is 
known as Exhaustive testing.
 
6. What is Early Testing? 
Defects detected in early phases of SDLC are less expensive to fix. So conducting 
early testing reduces the cost of fixing defects.

7. What is Defect clustering? 
Defect clustering in software testing means that a small module or functionality 
contains most of the bugs or it has the most operational failures.
--small module large chunk of defects or high defect density
 
8. What is Pesticide Paradox? 
Pesticide Paradox in software testing is the process of repeating the same test 
cases, again and again, eventually, the same test cases will no longer find new 
bugs. So to overcome this Pesticide Paradox, it is necessary to review the test 
cases regularly and add or update them to find more defects.
--test wear out 

9. What is Defect Cascading in Software Testing? 
Defect cascading in Software testing means triggering of other defects in an 
application. When a defect is not identified or goes unnoticed while testing, it 
invokes other defects. It leads to multiple defects in the later stages and results in 
an increase in a number of defects in the application. 
For example, if there is a defect in an accounting system related to negative 
taxation then the negative taxation defect affects the ledger which in turn affects 
other reports such as Balance Sheet, Profit & Loss etc.,

10. What are Quality Assurance and Quality Control?
Quality Assurance: It is process-oriented activities. It
ensures the prevention of defects ,in the process used to make Software Application.
So the defects don’t arise when the Software Application is being developed.
Quality Control: It is product-oriented activities. It executes
the program or code to identify the defects in the Software Application.
