Q. What is Software Testing? 

Software Testing is the process of evaluating and verifying that a software application or system meets the specified requirements and works as intended. 
It involves executing the software to identify defects, ensuring it is free from critical bugs, and confirming that it delivers the expected business value. 
• The main goals are: 
o Verification: Does the software meet the design specifications? 
o Validation: Does the software meet the customer’s needs? 
• Testing is not only about finding defects; it’s also about preventing defects and improving quality.

It’s the process that defines how software is planned, developed, tested, deployed, and maintained to ensure quality and efficiency.

Stage 2:  Requirement Analysis: The goal of the analysis part is to remove incompleteness and inconsistencies
(R.G:Identifying what the system should do)

process of understanding what the users need from a software system and defining those needs in a clear, precise, and actionable way.

Objectives of Requirement Analysis

Identify business goals and user needs.
✔ Ensures the system aligns with organizational objectives and solves real user problems.

Define functional and non-functional requirements.
✔ Functional: what the system should do (features, operations).
✔ Non-functional: how the system should perform (performance, usability, reliability, etc.).

Detect and resolve conflicts or ambiguities in requirements.
✔ Helps ensure clarity, consistency, and agreement among stakeholders.

Establish a clear scope for the project.
✔ Prevents scope creep and defines project boundaries early.
(Scope creep means the uncontrolled expansion or change in a project's scope — that is, when new features, requirements, or tasks are added after the project has already started, without proper review, approval, or adjustment of time, budget, or resources.)

Provide a baseline for design and validation.
✔ The requirements document serves as the foundation for system design, development, testing, and validation.



 Step1️⃣         Categorize and Organize Requirements 
 Description :Group raw requirements collected from interviews, surveys, documents, etc., into logical categories.
 Example:     Functional vs Non-Functional, Business vs 																															  System, etc.

2️⃣      Prioritize Requirements	
Decide which requirements are most important or urgent to implement first.	
Must-have, Should-have, Could-have, Won’t-have (MoSCoW)

3️⃣    Analyze Feasibility			
Check if each requirement is technically, economically, and operationally possible.	
Can we integrate this with existing systems? Do we have budget/time?

4️⃣    Model the Requirements (Process / Data Models)	
Create visual representations of requirements — helps understand workflows and data.	
Use case diagrams, DFDs, flowcharts, ER diagrams

5️⃣     Define and Specify Requirements Clearly	
Convert gathered inputs into clear, unambiguous statements.	
“The system shall send an email notification after approval.”

6️⃣    Validate Requirements	
Review with stakeholders to confirm that requirements are correct, complete, and aligned with business goals.	
Conduct review meetings, walkthroughs, or sign-	offs

7️⃣     Manage Requirement Changes	
Track updates, additions, or deletions of requirements during the project.	
Use change request forms, version control, requirement traceability matrix

Stage 5 :Testing : During each integration step,
 previously planned modules are added to the partially integrated system and the resultant system is tested. 
Finally, after all the modules have been successfully integrated and tested, the full working system is obtained and system testing is carried out on this. System testing consists of three different kinds of testing activities as described below.

Alpha testing: Alpha testing is the system testing performed by the development team.

Beta testing: Beta testing is the system testing performed by a friendly set of customers.

Acceptance testing: After the software has been delivered, the customer performs acceptance testing to determine whether to accept the delivered software or reject it
Once the software has been thoroughly tested, it's time to deploy it to the customer or end-users

SDLC Testing Phase – Sub-Steps, Purpose, and Examples

Step 1: Test Planning  
Purpose: Define testing strategy, objectives, scope, resources, and schedule.  
Example: Prepare a Test Plan for Login and Fund Transfer modules.

Step 2: Test Case Design  
Purpose: Create detailed test cases and conditions based on requirements.  
Example: Write test cases for valid/invalid login and transaction limits.

Step 3: Test Environment Setup  
Purpose: Configure hardware, software, and data for testing execution.  
Example: Set up QA server with test database and application build.

Step 4: Test Data Preparation  
Purpose: Create sample data to execute test cases effectively.  
Example: Prepare dummy users, accounts, and transaction records.

Step 5: Test Execution  
Purpose: Run test cases manually or using automation tools.  
Example: Execute test cases for fund transfer and check results in DB.

Step 6: Defect Logging & Tracking  
Purpose: Record and monitor any defects or issues found during testing.  
Example: Log failed transactions in Jira and assign them to developers.

Step 7: Defect Re-testing & Regression Testing  
Purpose: Verify fixed defects and ensure new changes don’t break existing functions.  
Example: Re-test login bug fix and run regression on account creation.

Step 8: Test Reporting & Closure  
Purpose: Summarize results, defects, coverage, and quality status.  
Example: Create Test Summary Report showing 95% pass rate and 5 open defects.

Stage 6 : Maintenance : Software Maintenance refers to the process of modifying and updating a software system after it has been delivered to the customer
involving planned and unplanned activities to keep the system reliable and up-to-date
 => Several Key Aspects of Software Maintenance

1.Bug Fixing: The process of finding and fixing errors and problems in the software.
2.Enhancements: The process of adding new features or improving existing features to meet the evolving needs of the users.
3.Performance Optimization: The process of improving the speed, efficiency, and reliability of the software.
4.Porting and Migration: The process of adapting the software to run on new hardware or software platforms.
5.Re-Engineering: The process of improving the design and architecture of the software to make it more maintainable and scalable.
6.Documentation: The process of creating, updating, and maintaining the documentation for the software, including user manuals, technical specifications, and design documents.

• Waterfall Model :
phases: requirement Analysis

Sequential and linear — each phase must complete before the next begins.
Works well when requirements are clear and fixed.
Difficult to handle changes once development starts.
🧠 Example: Used in government or legacy enterprise projects.(in government or legacy enterprise projects because it supports fixed requirements, strong documentation, and a controlled, predictable development lifecycle)

Features of Waterfall Model :
1.Sequential Approach: each phase of the project is completed before moving on to the next one.
2.Document-Driven :The waterfall model depended on documentation to ensure that the project is well-defined and the project team is working towards a clear                                                                                            set of goals. 

3.Quality Control:The waterfall model places a high emphasis on quality control and testing at each phase of the project, to ensure that the final product meets the requirements and expectations of the stakeholders

4.Rigorous Planning:  The waterfall model involves a careful planning process, where the project scope, timelines, and deliverables are carefully defined and monitored throughout the project lifecycle.


Advantages of the Waterfall Model

Simple and easy to understand.
Works well when requirements are fixed.
Clear structure and stages.
Easy to manage due to rigidity of model.
Good for small projects.
Milestones are easily set and tracked.
Early system design and resource planning is required.
Documentation is thorough and helps in maintenance.

Disadvantages of the Waterfall Model :
Not suitable for changing requirements.
No working software produced until late in the lifecycle.
High risk and uncertainty.
Poor model for long and complex projects.
Hard to estimate time and cost in later stages.
Limited client involvement after initial phase.
Errors in early phases can be costly to fix later.
Less flexibility in accommodating updates or feedback.

• Spiral Model

The exact number of loops of the spiral is unknown and can vary from project to project. 
Each loop of the spiral is called a phase of the software development process.

Extension of Waterfall — each development phase has a corresponding testing phase.
Testing starts early (test planning happens during design).
🧠 Example: Good for safety-critical systems like healthcare or automotive.

Defination :
The Spiral Model follows an iterative development process where the project passes through repeated cycles (called spirals) instead of a single linear flow.
Each spiral represents one phase of development, and every loop consists of 4 main activities.

| **Activity**                               | **Description**  
                                                                                                                                                       
| **1. Planning**                            | Identify objectives, alternatives, and constraints for the current phase. Includes project planning, resource                                                         						estimation, scheduling, and defining system requirements. |


| **2. Risk Analysis (Risk Assessment)**     | Analyze and identify potential risks, uncertainties, or problems that could affect the project. Evaluate 						alternatives and develop strategies to mitigate those risks.   |


| **3. Engineering (Development & Testing)** | Design, develop, and test the product for that iteration. This may involve prototyping, coding, and verifying 						the features defined during the planning phase.           |


| **4. Evaluation (Customer Review)**        | Present the developed product or prototype to the customer for feedback and evaluation. The customer’s 							feedback is then used to plan the next spiral (iteration).       |


✅ Benefits of the Spiral Model:
Strong risk management
High degree of customer involvement
Flexibility to adapt to changes
Early proof-of-concept for critical components through prototyping 

Advantages of Spiral Model
Risk Handling – Best model for identifying and reducing risks early in the project.
Flexibility in Requirements – Changes can be added at any stage.
Customer Feedback Oriented – Client is involved in every iteration.
Good for Large & Complex Projects – Suitable for long-term, high-budget, high-risk projects.
Prototyping is Built-in – Each cycle delivers a working prototype.
Better Progress Visibility – Each loop gives a clearer picture of project status.
Quality is Improved – Repeated testing and refinement in every phase.
Early Software Development – Partial versions of software are produced early.
Supports Reuse – Previous components and modules can be reused.
Structured + Iterative – Mixes features of waterfall and incremental models.

❌ Disadvantages of Spiral Model

Expensive & Time-Consuming – Costly due to repeated phases and risk analysis.
Requires High Skill – Risk assessment needs expert professionals.
Not Suitable for Small Projects – Overkill for low-budget or simple projects.
Complex to Manage – Requires excellent documentation and control.
Undefined Number of Phases – No fixed end point, cycles may continue indefinitely.
Customer Dependency – Regular involvement of client is mandatory.
Risk of Mismanagement – Incorrect risk analysis may lead to project failure.
Difficult to Use for Tight Deadlines – Iterative loops make planning harder.
Heavy Documentation – Every cycle requires review, approval, and documentation.

🔎 When Spiral Model is Best Used?

✔️ Large systems (banking, defense, aerospace,Battlefield Communication System (Secure Military Network))
✔️ High-risk software (safety-critical apps, AI systems)
✔️ Projects where requirements evolve over time
✔️ Projects requiring regular customer feedback eg.banking appliocation

| Spiral Loop | Output                      |
| ----------- | --------------------------- |
| 1st Loop    | Requirement + Risk Analysis |
| 2nd Loop    | Login prototype             |
| 3rd Loop    | Core banking operations     |
| 4th Loop    | Security + Encryption       |
| 5th Loop    | Final deployment            |

• Prototype Model
SDLC approach where an early working model / simplified model / mock-up of the software  is built to collect user feedback and 
refine requirements before full development starts.
Shows basic features, screens, or workflows to refine their expectations.
Example: A startup MVP (Minimum Viable Product) or AI-based prototype to test user interest.,ATM Prototype
interactive prototypes (using tools like Figma or Adobe XD)

Prototype Model Flow:
1. Collect Requirements
2. Build Quick Prototype
3. User Evaluates Prototype
4. Modify Prototype Based on Feedback
5. Repeat Until Approved
6. Develop Final System

✅ Advantages of Prototype Model

Improves Requirement Understanding
Users can see a working model and refine requirements.
Early User Feedback
Users interact with the prototype and suggest changes early.
Reduces Risk of Failure
Ambiguities and missing features can be found before full development.
Better Communication with Client
Visual output is easier to understand than documents.
Faster Initial Development
A basic product is built quickly for demonstration.
High Customer Satisfaction
Final system is more accurate because user feedback is utilized.
Helps in Testing & Validation
Prototype can be used to test design and logic earlier.

❌ Disadvantages of Prototype Model

Time-Consuming if Repeated Many Times
Constant changes can delay the actual development.
Higher Cost than Expected
Extra effort required to build multiple prototypes.
Poor Documentation
Developers may focus on prototype more than documentation.
Users May Think Prototype = Final System
Prototype is often incomplete and may mislead clients.
Prototype May Be Poorly Designed
Quick implementation may ignore quality or scalability.
Not Suitable for Large, Complex Systems
Too many requirements changes can make it messy.

Q . Difference between Verification and Validation. 
• Verification ensures the product is built according to the requirements and design. It answers, “Are we 
building the product right?” 
Example: Reviewing documents, inspecting code. 

1.Reviewing requirement documents to ensure:
Tax calculation rules match government regulations
Discount logic follows store policies

2.Checking database design to confirm:
Inventory tables correctly track stock levels
Customer tables include loyalty points fields

3.Code reviews to ensure:
POS billing module follows the defined algorithm
Security standards are applied to payment modules

• Validation ensures the product meets the actual needs of the user. It answers, “Are we building the 
right product?” 

Product Master :
New products added appear correctly on POS and website
Price, tax, and barcode updates reflect instantly during checkout
Product availability updates correctly after every sale
Sales reports generate correctly by store, product, and date
Inventory reports update accurately after each sale or purchase
Promotion performance reports reflect correct discount usage

✔ POS is offline / in-store
✔ Cashier scans product : Stock quantity decreases 
✔ Sale updates admin panel
✔ Reports are generated

Example: Testing the application with real-world scenarios.

(involves running the code).

• Hybrid Model
The Hybrid Model is an SDLC approach that combines features of two or more models — for example, Waterfall, V-Model, and Agile — to create a process that best fits the project’s requirements.

In this model, some phases may follow a sequential approach for stability (like requirement analysis and design), while development and testing may follow iterative cycles to deliver faster feedback and improvements.
The main goal of the Hybrid Model is to leverage the strengths of each model while minimizing their weaknesses, ensuring both quality and adaptability.

1. Requirements Gathering (Prototype Iterations)

Meet users (doctors, nurses, admins, patients) to gather requirements.
Build initial UI prototypes — simple screens showing how the system will look and behave.
Collect feedback from users.
Refine and modify the prototype multiple times until the requirements are confirmed.
Ex:
A prototype of the appointment scheduling system is created. 
Doctors review it and 
suggest adding “patient history” visibility on the same screen. 
The design is updated before development begins.

2. System Design (V-Model)

Create high-level and detailed design documents.
Define data flow, system architecture, and module interactions.
Plan test cases for each design phase (as per the V-Model’s “Verification” side).
Map each requirement to a corresponding validation step.
Ex
Designing how data flows from patient registration → doctor consultation → billing → pharmacy while maintaining data security (HIPAA compliance).

3. Module Design & Coding (V&V – Verification)

Break the system into smaller modules (e.g., Billing, Pharmacy, Doctor Scheduling).
Write code for each module based on the design.
Perform unit testing for each module to verify it works as expected.
Ensure code meets software quality standards.
Ex:
Develop the Billing Module — ensure it correctly calculates charges, taxes, and generates invoices. Unit testing verifies each function works properly.

4. Integration & Validation (V&V – Testing Phases)

Combine all verified modules (integration).
Perform integration testing to ensure modules interact correctly.
Conduct system testing to check the entire application workflow.
Validate that all requirements (defined from prototype phase) are satisfied.
Ex:
Integrate the Patient Registration, Appointment, and Billing modules. Validation confirms that when a patient registers and visits a doctor, billing and record updates happen automatically.

5. User Evaluation (Prototype)
Conduct User Acceptance Testing (UAT) sessions.
Users test the system with real scenarios.
Collect user feedback for usability or design improvements.
Refine user interfaces or small features using prototype iterations again.
Example (HMS):
Nurses and doctors use the system in a test environment. They suggest increasing text size on patient dashboards and adding a “search by patient ID” shortcut — changes are made before go-live.

6. Deployment & Maintenance
Deploy the application in the hospital’s live environment.
Train end-users (staff, doctors, receptionists).
Monitor the system and fix any bugs reported.
Continuously gather feedback and make minor improvements through small prototypes or patches.
Example (HMS):
After deployment, hospital staff use the system daily. Later, an update adds a new “Digital Prescription” module developed and tested using the same V&V + Prototype cycle.

Types of Compatibility Testing by Application Type
1. Web Application
Test the website on multiple browsers and versions (e.g., Chrome, Firefox, Edge, Safari).

Check responsive behavior on different screen resolutions and devices (desktop, tablet, mobile).

2. Client-Server Application
Verify compatibility between different client configurationhos and the server environment.
Test how the application behaves with varied network speeds, different OS versions, and database servers.
Example:
✅ Test a banking client app installed on Windows 10 and Windows 11 connecting to the same core banking server.

3. Stand-Alone Application
Ensure installation and performance are consistent.
Example:
✅ Test a loan calculator desktop app on Windows 8, 10, and 11 with different screen resolutions.

🌐 Cross-Platform Compatibility Scenarios
a. Multiple Browsers on One OS
Test the web app in Chrome, Edge, Firefox, Safari — all on the same OS (e.g., Windows 11).

Example:
✅ Banking login and fund transfer pages behave identically in all browsers on Windows.

b. Multiple OS on One System
Using virtual machines or containerization tools (like VMware, Docker), run different OS on one system and test the app.
Purpose: Validate the application’s stability and look/feel on multiple operating systems.
Example:
✅ Test banking web portal on Windows 11, Ubuntu, and macOS (same hardware via VMs).

o What is Soak Testing / Endurance Testing?
Running a system at high load for a prolonged period of time to identify the 
performance problems is called Soak Testing.
testing an online banking system:
You simulate 500 concurrent users continuously performing transactions (balance checks, transfers, logins)
Run the test for 48 hours non-stop
During this time, you monitor:
Memory usage (does it keep increasing?)
CPU utilization (does it stabilize or stay high?)
Response time (does it get slower over time?)
Any crashes or database disconnections

✅ The system should remain stable, responsive, and consistent throughout the test period — no memory leaks or slowdowns.

-----------------------------------------------------------------------------------------------------
o Spike Testing
online banking site normally handles 1,000 users.
During Spike Testing, you simulate:
A sudden jump from 1,000 to 5,000 users in a few seconds (e.g., salary day).
After some time, reduce it back to 1,000 users again.
You observe:

Does the system crash or slow down when load spikes?
Does it show proper error messages (e.g., “Server busy”)?
How fast does it recover when load returns to normal?

✅ The system might slow briefly but should not crash — and should recover automatically when load decreases.

Q.What is Regression Testing?

Repeated testing of an already tested program, after modification, to discover any 
defects introduced or uncovered .
1. New functionalities are added to the application
2. Change Requirement (In organizations, we call it as CR)
3. Defect Fixing
4. Performance Issue Fix
5. Environment change (E.g., Updating the DB from MySQL to Oracle)

o Unit Regression testing :usually a single module or feature where the change happened.
Developer fixed a bug in the “Interest Calculation” logic inside the Loan Module.
✅ Tester performs unit regression only on:
The Loan calculation screen
The interest formula validation
No need to test login, fund transfer, etc. — only that specific module

o Regional Regression testing :group of related modules (region) that are functionally connected to the changed module
Fund Transfer (main change area)
Account Balance Update
Transaction History
Notifications (SMS/Email)
These are related features — all may be affected by the change

o Full Regression testing:entire application end-to-end to ensure no part of the system is broken by recent changes
Login & Authentication
Account Summary
Fund Transfer
Loan, Cards, Investments
Reports, Notifications, etc.

 If the bug is a valid defect the development team will fix it.

release then the defects are postponed 
 If the defect or bug is raised earlier then the tester will assign a DUPLICATE status 
 When bug is assigned to developer to fix, it will be given a IN-PROGRESS status 
 Once the defect is repaired, the status will change to FIXED at the end the tester will give 
CLOSED status if it passes the final test.
